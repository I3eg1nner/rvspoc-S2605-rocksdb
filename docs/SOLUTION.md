# S2605 方案说明：RocksDB v11.1.1 的 RV64GCV 移植、验证与测量

## 一、约束，以及由它推出的设计

移植面对三个无法回避的事实：评测机 LX5000 不可访问，其 VLEN 与可选扩展（Zbc/Zvbc 等）未知；评测工具链未知，clang ≤19 缺少向量密码 intrinsics；持久化格式（CRC、bloom 位图、哈希）一旦与标量实现不一致，数据在新旧版本间不可互读。三个事实分别推出三条设计决策。

**扩展未知 → 运行时分派阶梯。** 每种能力依赖都在运行时用
hwprobe(2) 探测，缺失时降级到下一级实现而非失败。CRC32C 是完整形态：Zvbc 向量 clmul 折叠（K3 实测 4KB 块 8.1 倍）→ Zbc 标量clmul 折叠（6.4~7.0 倍）→ slice-by-8 原实现。中间层的存在改变了风险结构：向量扩展缺失的代价从"退回 1 倍"变为"退到 6 倍"。

**工具链未知 → 构建期探测编译能力本身，指令用编码写死。** Makefile
对 CRC 向量 TU 的启用判据不是 march 字符串被接受，而是一段`vclmul` intrinsic 能否真的编译——clang 18/19 接受`-march=..._zvbc` 却没有对应 intrinsic，探测 march 会导致构建失败，探测编译则自动优雅排除。Zbc 层更进一步：`clmul/clmulh` 以 raw `.insn` 编码写出，任何汇编器都能通过，执行与否交给运行时探测。

**格式必须位相同 → 常数不可信任，产出必须闭环验证。** CRC 折叠
常数不从任何来源拷贝：启动时对照逐位参考实现用 GF(2) 消元现场求解，再经软件 clmul 自验证；验证失败则该层永不启用。因此探测或推导出错的后果被限定为性能回退，不可能是错误数据。位相同性另由"标量构建写库、向量构建读库"的双向交叉验证覆盖。

在这三条之外还有一条为后文服务的决策：**每个 kernel 都有独立开关**（编译期宏、运行时探测、环境变量三级）。它的直接动机是部署保险，但更重要的后果在第三节——性能归因需要把配置空间逐维拆开，没有独立开关就没有归因实验。

**异构多核（赛题点名的第二个优化方向）**：思路是把吞吐型后台
工作（compaction/flush）与延迟敏感的前台读写分离到不同核簇——LX5000 是 32 性能核 + 16 能效核，compaction 抢占前台核与内存带宽正是 P99 的直接威胁。实现为 RocksDB 后台线程池的亲和性钩子（util/threadpool_imp.cc）：按池设环境变量`ROCKSDB_BG_{LOW,HIGH,BOTTOM}_CPUS` 即可把对应线程 pin 到指定核簇，不设则行为与原版逐字节一致（riscv-only、默认关闭、非 riscv 构建预处理不变）。配套交付了评测机上的 P/E 簇发现方法（读cpufreq policy 的 max_freq 分簇）与前台 taskset 配方，见REPRODUCE.md"异构多核"节。诚实声明：该机制在我们的 K3 上**无法产生有效 A/B 数字**——K3 的 8 个 A100 协处理核被内核保留（用户态affinity 直接 EINVAL），可调度核只有同构的 8 个 X100，没有异构簇可分离；机制的正确性已验证（变量解析/绑核路径），收益幅度只能在评测机的真实 P/E 拓扑上兑现。这也是所有单线程测点必须 taskset绑核的原因：不绑核时 t1 基准可能落到能效核，基线与优化档双向失真（REPRODUCE 中列为测量告诫）。

默认启用的改动：CRC 三层阶梯、Slice 比较的 RVV 首异定位、FastLocalBloom 探测向量化、Zbb 无分支 varint32 解码、索引块restart-key 前缀旁路、二分探测双路 prefetch（zicbop）、自旋pause hint。实现存在但默认关闭：XXH3/XXPH3 RVV 分支与 16 字节内联短 key 比较——差分测试全绿，K3 配对测量为负收益，按第三节的裁决规则关闭，开关保留。

## 二、正确性验证：闸门由风险推出

向量代码特有的错误模式决定了闸门的形状。

尾部与掩码处理错误只在特定 VLEN 下显形，且在"脏 lane 恰好是旧值"时被掩盖——对应的闸门是 QEMU vlen=128/256/512 三档矩阵，每档开启`rvv_ta_all_1s,rvv_ma_all_1s`（尾部与被掩 lane 强制全 1）。这一设计在 vlen=128 档捕获了一个实际缺陷：bloom 探测循环假设 vsetvl授予数等于请求数，VLEN=128 下授予减半导致假阳性。修复之后，"授予数 ≠ 请求数"成为后续所有 kernel 差分 harness 的固定测试项——一次捕获转化为一条前置检查。

差分测试对照的参考实现刻意与被测实现无共享代码（CRC 用逐位实现，varint 用原 fallback），覆盖非 VL 整数倍长度、未对齐起点与分段恢复链。全量 `make check` 的现存证据为：29589 个并行用例全部执行，唯一失败项 prefetch_test 在同板同树的纯标量构建下复现出逐位相同的断言值与相同的段错误，故归因于环境敏感的统计断言而非向量代码。（此前一轮全过记录因原始日志在磁盘清理中丢失而无法复核，已作废并以本次留痕运行取代——结论的效力以可复算的证据为限，这一原则同样适用于我们自己的历史结论。）

基线侧有一条机械判据：标量基线二进制必须满足`objdump -d db_bench | grep -c vsetvli == 0`。它先后否决了两个不合格的基线：发行版 gcc 默认 march 含 V，"标量"构建被静默向量化；PORTABLE 构建中按设计常驻的 CRC 向量 TU 使二进制含向量指令。后者促成 `RISCV_NO_RVV_CRC32C` 开关，由此得到零向量指令的基线 S0——第三节所有对比的锚点。

## 三、性能测量：方法由误差来源推出，结论由排除法收紧

### 3.1 误差来源与协议

直接比较两次运行的 db_bench 输出，同一二进制的波动可达 ±5%：LSM树状态、页缓存、后台 compaction 都随时间变化。因此所有 A/B 采用同会话交错：同一数据库、两臂按拉丁方轮换、暖机弃置、运行前静板（idle 阈值与进程黑名单）、二进制记录 sha256。判定标准在数据产生之前固定——中位数方向加逐轮符号计数，不足则判 INCONCLUSIVE 并默认关闭。标准先于数据，是为了让"达标"不可被事后定义。

### 3.2 一个矛盾及其分解

初版交付配置（RVA23 子集 march + O3 + PGO + 全部 kernel）对标量 -O2 基线的增益为 +10%~+27%。这组数字混合了两类来源：O3 与PGO 属于任何架构都可获得的通用编译收益，march 与 kernel 属于RISC-V 专有工作。二者必须分开，否则"RVV 优化的收益"无从谈起。

分离的手段是三臂对照：S0（stock 等价标量 -O2）、SP（同源 + O3+PGO，无任何 riscv 专有改动）、GP（当时的交付二进制）。测量结果构成一个矛盾：SP 按中位数在全部五个测点超过 GP（逐轮符号 6/6、6/6、4/4、3/3、2/3）——若 riscv 专有工作的净贡献为正，这不应发生。

矛盾有三种候选解释：全局向量 march 的自动向量化在该负载上为负；某些 kernel 在 O3+PGO 的内联与布局下变为负资产；GP 所用的 PGO profile 训练于数天前的另一会话，已经失效。三种解释可以逐一检验，因为每一维都有独立开关：

- 只加全局 march（V1）：相对 SP 损失 0~2 个点——march 不是主因；
- 只加 CRC 阶梯（V3）：与 SP 持平——CRC 无代价；
- 在第二块 K3 上做单变量拔除：从 V5（当时的候选交付形态，≈SP加非向量 kernel 全集）中移除 sidecar 与二分 prefetch，read 反而下降 8~10%（逐轮 0/5、0/3）——kernel 组合不是负资产，方向相反；
- 同一交付配置以当前板况重新训练 PGO（V2）：反超 SP，读 +9.5%（5/5）、seek +5.1%（5/5）、单线程读 +17.6%（3/3）。

前三项排除了前两种解释，第四项直接证实第三种：**陈旧的 PGO profile 足以使同一配置从领先变为落后 3~10 个点**。该结论产生两个输出：REPRODUCE.md 将"PGO 在目标机上现场训练"列为硬性步骤；归因账目就此分离——通用 O3+PGO 贡献 +11~20 个点，riscv 专有工作在其上净增读/seek +5~+18%（逐轮符号一致）。

### 3.3 终版数字

终版对比为 S0 对 V2 的同会话直接配对（非链式换算）。S0：零向量指令、全部工程路径禁用的 stock 等价基线；V2：RVA23 必选扩展子集march（含 zicond）+ O3 + 现场新鲜 PGO + 裁决后 kernel 集。

| 测点 | S0 → V2 | 逐轮符号 |
|---|---|---|
| readrandom t1 | **+31.6%** | 4/4 |
| readrandom t8 | **+26.1%** | 6/6 |
| seekrandom t1 | +24.3% | 4/4 |
| seekrandom t8 | +21.1% | 6/6 |
| fillrandom t1 | +4.0% | 4/6（混合） |
| P99（read t8，--histogram） | 41.6 → 33.9 µs（**−18.6%**） | 直方图在档 |

关于 zicond 的一个已知环境事实：它是 RVA23U64 必选扩展（LX5000必有），但赛题推荐测试环境 QEMU `-cpu rv64,v=true,vlen=256` 默认关闭它（8.2 与源码自建的 11.1.1 均实测），含 czero 的 V2 在该命令行下会非法指令。构建因此做成**自适应**：原生构建逐项探测本机扩展自动组装 march（评测机上一条命令即得正确配置），交叉/QEMU 目标构建落无 zicond 安全集——QEMU 安全变体 V2Z同协议实测 read t1 +29.5%、fill +6.4%（6/6）、P99 −21.2%，并已在 QEMU 11.1.1 按赛题原样命令行端到端跑通（证据 profile/evidence/qemu-compat/）。

按"三项各自 ≥30%"的最严口径：readrandom t1 **+31.6% 达标**（QEMU安全变体 V2Z 为 +29.5%，贴线），readrandom t8 与 seekrandom 未及，fillrandom 差距显著。

fillrandom 的差距可以从火焰图直接解释：写路径的最大热点是skiplist 指针追逐（13.8%）与比较器（15.1%），二者的开销是依赖链上的 DRAM 延迟——向量指令不作用于此，软件预取无法预取尚未加载的next 指针（上游预取点已被 zicbop 激活并计入现有数字）。计算型kernel 单点加速 8 倍，在此类负载中折算到端到端仅 1~2%。写侧的上限由负载结构决定。

## 四、结果的适用边界

**平台**：全部测量在 SpacemiT K3（VLEN 256、8×X100）完成；LX5000
（DDR5、48 异构核）的热点占比无法由 K3 外推。分派阶梯保证的是正确性与"落在哪一级"，不保证收益幅度。

**PGO 的现场性**：headline 依赖评测机上现场训练；若评测流程不允许
现场训练，退化幅度可由 ACCEPTANCE 二节归因表的 GP 行估计（−3~−10 个点）。

**RocketMQ 5.5.0 的 JNI 部署**（赛题硬性要求）：这一步不是打包
动作而是移植工作——RocketMQ 5.5.0 的 DefaultMessageStore 无条件初始化 RocksDB 存储，而其捆绑的 rocketmq-rocksdb-1.0.6.jar **不含riscv64 原生库，broker 在 riscv64 上无法启动**。解法：用本树`make rocksdbjava` 构建 rocksdbjni-11.1.1（RVV 档，含全部分派阶梯）整包替换 lib/ 下的捆绑 jar，另对 JDK21 做脚本适配（runbroker/ runserver 压堆、去 JDK8 时代 flags、小内存板上MaxDirectMemorySize 压到 2g）。部署步骤在 REPRODUCE.md，jar 的sha256 身份链逐格记录在 profile/rmq-matrix/jar-identity.txt。下文全部 RocketMQ 数据都跑在这套部署之上——broker 能在 riscv64 上带RocksDB 存储启动并扛过压测，本身就是该要求的验收证据。

**RocketMQ 的 TPS 与 P99**（赛题指定的最终评测指标）：60 分钟高压
测试 avg Send/Consume TPS = **6056 / 6117**（361×10s 采样全量归档、独立复算一致），失败计数器全程 0、无 OOM。24 格双臂矩阵（3 尺寸 × 2 场景 × AB/BA）显示两臂 TPS 总体在 ±1.5% 噪声带内——RocksDB 不是1K/128K 消息路径的瓶颈；16K backlog（写入与排空并发、存储压力最大）RVV 档 send TPS **+5.9%** 为唯一显著优项，128K 饱和场景精确 put记账 **−3.9%** 为唯一显著劣项。因此矩阵支撑的硬结论是稳定性（零丢失链全绿），TPS 上不主张系统性优势；逐场景数表与 24 格 MANIFEST在 ACCEPTANCE 二 b。P99 的本地证据来自 db_bench 直方图（3.3 节主表 −18.6%，V2Z 为 −21.2%）；RocketMQ 自带 benchmark 不输出分位数，RocketMQ 侧无 P99数据，如实声明。

**样本量**：每测点 3~6 轮配对，稳健性以逐轮符号一致性表述而非
置信区间；原始行全部在 benchmark.csv；headline 五个百分比已由独立审计 agent从原始行复算，与文档逐位一致。

**否决记录**：candidates.jsonl 保留每个被拒候选及其数据（xxhash
负收益、短 key 内联层被 RVV vfirst 路径反超、LTO 单独启用高方差无结论未采用、zvbb 加入 march 后编译器未发射任何向量位操作指令）。RocketMQ 矩阵过程中排除的五个环境级障碍（broker 冷启流控、riscv64 JDK21 C2 JIT崩溃、rocksdbjni 向 tmpfs 泄漏 404MB/次、客户端冷启单发超时、128K大消息饱和）逐一留痕，被替换的实验格以 `*.SUPERSEDED`、`*.CRASHED`后缀保留原目录。

## 五、生产方式：LLM Wiki、Self-Improving Agents 与 Human-in-the-Loop

这份工作由三个相互制衡的机制协作产出。三者不是工具关系——每一方都在补另外两方的结构性短板，缺任何一方，前四节的结果都会以可指出的方式劣化。

**LLM Wiki：结构化知识库补模型的记忆与幻觉短板。** 大模型跨会话
没有记忆，且在知识边缘倾向于给出听起来合理的答案。知识库（rvv-wiki，三层语料：上游源 → 综合页 → 索引）用两个机制对冲：其一，每条知识带双轴标签（置信度 verified→experimental、可复现性concept→benchmarked）并挂接到源层——引用一条知识必须连标签一起引用，"微基准语境的 verified"和"推断"在决策中权重不同；其二，工作契约要求先查库再设计、超出覆盖范围时输出"无覆盖"而非外推。实效可指认：bloom 单 key 的 vluxei 形态被库中"实测慢 7~9 倍"的记录直接否决，省去一轮实现-测量-拒绝；"vsetvl 授予数 ≠ 请求数"作为已归档 pattern 预先进入差分 harness 设计，第二节那个 vlen=128缺陷才会在 QEMU 而不是评审机上显形；CRC 折叠 kernel 连同差分测试自库中工件移植，上板即 8.1 倍。反方向的流动同样是制度：本项目产出的 9 条运行记录、2 个新 pattern、2 条方法论条目已写回并通过库的校验器——下一个项目的冷启动点比本项目更高。

**Self-Improving Agents：把失败固化为规则，用独立上下文替代自证。**
模型评估自己产出的东西时缺乏对抗性。本项目用两类外部化机制替代"自我审查"。第一类是规程：判定标准在数据之前落盘（3.1 节），使"达标"不可被产出方事后定义；台账只增不删（candidates.jsonl 的拒绝行、benchmark.csv 的 INVALID 行、被替换实验格的原目录），使不利证据无法消失；标量基线设 objdump 零向量指令绊线。第二类是
**不共享上下文的独立 agent**：合规审计 agent 对照赛题原文逐条打开
证据文件，从原始数据复算 headline 五个百分比（逐位一致），并发现执行方自查未发现的缺口（60 分钟压测原始日志由此回收归档）；组件筛查 agent 在第二块板独立完成单变量拔除实验，是 3.2 节排除法的关键一环；文本 review agent 抓出 31 处表述问题，含两处会动摇headline 口径的改稿残留。"自我改进"的确切含义是失败转化为永久防线而非一次性修复：跨轮次噪声 → 同会话交错协议；陈旧 PGO profile 拖累 3~10 点 → "目标机现场训练"写入 REPRODUCE 硬性步骤；vsetvl 授予数缺陷 → 后续所有 kernel harness 的固定测试项。

**Human-in-the-Loop：价值判断与不可逆决策保留给人。** 模型可以
枚举选项并给出证据权重，但三类决策在结构上属于人：评价口径的裁定（"30% 按三项各自计"的最严解释是人的选择，直接决定第四节达标结论的写法）；不对称赌注的取舍（"RVA23 若有 Zbc 不做就亏了"促成 CRC 标量 clmul 中间层，成为工具链风险的 6 倍保险；zicond 的去留与自适应构建的最终形态同样由人裁定）；不可逆动作的放行（PR提交时点由人持有）。人的另一个作用是引入外部对抗视角：多轮外部评审被逐条转入执行，其中"通用编译收益是否被计入 RVV 收益"的质询直接触发 3.2 节的三臂对照——本项目最重要的单个发现（陈旧 profile根因）位于这条质询的延长线上。

三者的耦合点是**文件而非对话**：契约、计划、台账、证据目录都在仓库里，每个会话（包括独立 agent）从文件冷启动，对话中断不丢失状态。这也是披露的载体——赛题要求说明 AI 参与方式与份额，本仓的回答是：约 99% 的代码与文档由模型生成，而**框架属于人**——上述方法论与治理结构（知识库体系、预注册规程、独立审计的组织方式）由人提出并搭建，外加 15 处以上的方向性裁定；模型在框架内执行。全部过程可从 git 历史、候选台账与知识库引用轨迹中复原。
