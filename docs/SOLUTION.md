# S2605 方案说明：把 RocksDB 搬上 RV64GCV，以及我们如何两次差点骗了自己

这份文档讲三件事：我们对 RocksDB v11.1.1 做了什么；这些改动的正确
性与性能数字是怎么一步步被验证出来的（包括两次险些出错的经历）；
以及拿到这些数字的人应该怎么读它们。逐条赛题要求的对照清单在
docs/COMPLIANCE.md（由独立审计 agent 抓取官网原文逐项核实），全部
结果表与证据文件索引在 docs/ACCEPTANCE.md。

---

## 一、方案的骨架：三条设计规则

整个移植遵守三条规则，后面所有的故事都建立在它们之上。

**规则一：改动必须可整体拔除。** 所有 RISC-V 代码都躲在
`#if defined(__riscv)` / `__riscv_vector` 或运行时 hwprobe(2) 探测
之后。我们用一个苛刻的标准验证隔离性：非 riscv 平台的预处理输出
必须 token 级不变（aarch64 上实测比对过），x86 交叉构建逐字节不受
影响。这条规则不只是移植礼貌——它后来成了性能归因实验的物质基础：
因为每个 kernel 都能被单独关掉，我们才能回答"收益到底来自哪里"。

**规则二：能力探测逐级降级，任何一级缺失都落到正确的下一级。**
最典型的是 CRC32C。评测机 LX5000 的扩展清单我们拿不到，工具链也
可能是没有向量密码 intrinsics 的 clang，所以 CRC 做成三层阶梯：

1. **Zvbc 向量 clmul 折叠**——K3 上 4KB 块 8.1 倍（7.3 GB/s）；
2. **Zbc 标量 clmul 折叠**——指令用 raw `.insn` 编码写死，任何
   march、任何工具链都能编译，第二块 K3 上实测 6.4~7.0 倍，距向量
   档只差 15%。这一档的存在意味着：哪怕评审机没有 Zvbc、哪怕编译
   器把向量 TU 排除了，CRC 仍有 6 倍多；
3. **slice-by-8**——原实现，兜底。

折叠常数不抄任何魔数：启动时用 GF(2) 高斯消元对着逐位参考实现现场
求解，再用软件 clmul 自验证，验证不过该层永不启用——误探测的后果
是回退，而不是错误的数据。三层产出与标量实现逐位相同（标量写库、
向量读库双向交叉验证过），这保证了滚动升级和混合部署安全。

**规则三：每个 kernel 三级开关。** 编译期宏（`ROCKSDB_DISABLE_*`）、
运行时探测（hwprobe 的 V/Zbc/Zvbc 位）、环境变量（如
`ROCKSDB_RVV_CRC32C`）。听起来是工程冗余，实际上每一级后来都救过场。

在这三条规则之上，默认启用的改动有：CRC 三层阶梯、Slice 比较的
RVV 首异定位（vfirst）、FastLocalBloom 探测向量化、Zbb 无分支
varint32 解码、索引块 restart-key 前缀旁路（二分 seek 时前缀不等
就免解码）、二分探测的双路 prefetch（zicbop）、自旋等待的 pause
hint。另有两组实现**存在但默认关闭**：XXH3/XXPH3 的 RVV 分支和
16 字节内联短 key 比较——差分测试全绿，但 K3 上配对实测是负收益，
我们按数据关掉了它们，开关（`RISCV_RVV_XXHASH=1` 等）保留。

## 二、正确性是怎么守住的

每个 kernel 在上板之前要过同一套闸门：对照独立参考实现的差分测试
（覆盖非 VL 整数倍的长度、未对齐的起点、分段恢复链），在 QEMU 的
vlen=128/256/512 三档各跑一遍，而且每档都开着敌意标志
`rvv_ta_all_1s,rvv_ma_all_1s`——它会把尾部和被掩码的 lane 全部填 1，
专治"恰好没读到脏数据"的侥幸。

这套流程不是摆设。QEMU vlen=128 抓到过一个真 bug：bloom 探测循环
假设 `vsetvl` 请求多少就授予多少，在 VLEN=128 上授予数减半，直接
产生假阳性。修复后"授予数 ≠ 请求数"进了我们的知识库，后来写每个
新 kernel 时 harness 都会主动测这一点。

另一道闸门是全量 `make check`。这里有个值得讲的插曲：第三轮全过
的原始日志在一次磁盘清理中丢了，文档里"38934 项全过"一度成了无法
复核的断言。外部评审指出这一点后，我们在第二块 K3 上用交付树重跑
了一遍并这次留下全部证据：29589 个并行用例全部执行，唯一失败的
prefetch_test 用同板同树的**纯标量构建**复现出了逐位相同的断言值
和相同的段错误——失败与我们的向量代码无关，是环境敏感的统计断言。
旧口径就此作废，新数字每一位都能从归档的 joblog 里复算出来。

最后是一根"绊线"：标量基线构建必须满足
`objdump -d db_bench | grep -c vsetvli == 0`。它立过两次功。第一次
抓到发行版 gcc 默认 march 带 V、"标量基线"被静默向量化；第二次抓
到 PORTABLE 构建里按设计常驻的 CRC 向量 TU——为此我们新增了
`RISCV_NO_RVV_CRC32C` 开关，才得到真正一条向量指令都没有的基线
（下文的 S0）。

## 三、性能数字的来历：两次差点骗了自己

### 第一次：跨轮次比较

早期我们把不同轮次跑出的数字直接对比，直到发现同一份二进制在两轮
之间能差 ±5%——LSM 树的 DB 状态、页缓存、后台 compaction 都在变。
从那以后所有 A/B 都改成**同会话交错**：同一份数据库、两臂严格轮换
（顺序按拉丁方轮转防止顺序效应）、暖机弃置、跑前静板（idle 阈值 +
进程黑名单）、每个二进制记 sha256。判定标准在数据产生**之前**写死：
看中位数方向和逐轮符号计数，达不到就判 INCONCLUSIVE 并默认关闭——
不许事后挪球门。

### 第二次：把编译器的功劳记在自己头上

初版交付配置（RVA23 子集 march + O3 + PGO + 全部 kernel）对标量
-O2 基线的 headline 很好看。外部评审问了一个尖锐的问题：这里面有
多少是 O3 和 PGO 这种**任何架构都能拿到的通用收益**？

我们补了三臂对照：S0（真 stock 等价的标量 -O2）、SP（同源代码 +
O3+PGO，不含任何 riscv 专有改动）、GP（当时的交付二进制）。结果
令人清醒：SP 在全部五个测点上**超过** GP，逐轮符号 6/6、6/6、
4/4、3/3、2/3——纯标量加通用优化，比我们的交付还快 3~10%。

接下来是排障。嫌疑人有三个：全局向量 march 的自动向量化、某个
kernel 在 O3+PGO 世界里变成负资产、或者 GP 那份几天前训练的 PGO
profile 本身。我们把配置空间拆开逐一对照：只加全局 march 的 V1
（只损失 0~2 个点）、只加 CRC 阶梯的 V3（零成本）、在第二块板上
做的单变量拔除实验（拔掉 sidecar+prefetch 反而让 read 掉 8~10%，
kernel 无罪）……最后剩下的嫌疑人只有一个：**陈旧的 PGO profile**。
把同一份交付配置在当前板况下重新训练（V2），它立刻反超 SP：读
+9.5%（5/5）、seek +5.1%（5/5）、单线程读 +17.6%（3/3）。

这条教训值 10 个百分点："PGO 必须在目标机上现场新鲜训练"如今是
REPRODUCE.md 里的硬性步骤，也促进回了我们的方法论知识库。
顺带的收获是归因终于干净了：通用 O3+PGO 贡献 +11~20 个点，riscv
专有工作在其上再净增读/seek +5~+18%，两笔账分开记。

## 四、终版数字，以及怎么读它

终版对比是 S0 对 V2 的同会话直接配对（不是链式换算）：S0 是零
向量指令、全部工程路径禁用的 stock 等价基线；V2 是 RVA23 必选
扩展子集 march + O3 + 现场新鲜 PGO + 裁决后 kernel 集。

| 测点 | S0 → V2 | 逐轮符号 |
|---|---|---|
| readrandom t1 | **+31.6%** | 4/4 |
| readrandom t8 | **+26.1%** | 6/6 |
| seekrandom t1 | +24.3% | 4/4 |
| seekrandom t8 | +21.1% | 6/6 |
| fillrandom t1 | +4.0% | 4/6（混合） |
| P99（read t8，--histogram） | 41.6 → 33.9 µs（**−18.6%**） | 直方图在档 |

按赛题最严的读法（三项各自 ≥30%），read t1 过线，read t8 和 seek
差几个点，fill 差得远。我们如实报，不挑口径。

fill 的短板是结构性的，值得解释一下：写路径的火焰图顶端是 skiplist
的指针追逐（13.8%）和比较器（15.1%）——一条依赖链上的 DRAM 延迟，
向量指令帮不上忙，软件预取也无法预取还没读到的 next 指针（上游的
prefetch 点已经被我们激活并计入了）。计算型 kernel 哪怕单点快 8
倍，在这种负载里也只占端到端的 1~2%。这不是执行没到位，是负载的
本性。

RocketMQ 侧的定位要说清楚：60 分钟压测（361 个采样全量归档，均值
经独立复算与文档逐位一致）和 24 格双臂矩阵验证的是**稳定性**——
零 OOM、零损坏、零丢失，每格排空到零、失败门 fail-closed。它不是
性能证据：两臂 TPS 在噪声带内互有出入，而官方口径的 P99 我们只有
db_bench 直方图这一手证据，RocketMQ 自带的 benchmark 工具不输出
分位数，这个空缺文档里写得明明白白。

最后是几条读数时该记住的边界。所有测量都在 SpacemiT K3（VLEN 256）
上做的，评测机 LX5000 是另一颗芯片（DDR5、48 个异构核），热点占比
没法外推——分派阶梯保证的是"落在正确的一级"，不是收益幅度。headline
依赖评测机上现场训练 PGO；如果评测流程不允许，数字会退化，退化幅度
在归因表的 GP 行里有量化。每个测点 3~6 轮配对，我们用逐轮符号一致
性而不是置信区间说话，原始行全部在 benchmark.csv 里，谁都可以重算
——事实上独立审计 agent 就重算过一遍，逐位吻合。

被否掉的路也都留了尸检报告：candidates.jsonl 里每个被拒候选都带着
拒绝原因和数据（xxhash 负收益、shortkey 被自家 vfirst 反超、LTO 让
读掉 23%、zvbb 加进 march 后编译器一条向量位操作指令都没发射……）。
RocketMQ 矩阵路上排掉的五个环境级障碍（broker 冷启流控、riscv64
JDK21 的 C2 JIT 崩溃、rocksdbjni 每次启动往 tmpfs 泄漏 404MB、
客户端冷启单发超时、128K 大消息饱和）也全部留痕——被替换的实验格
连目录都带着 `*.SUPERSEDED`、`*.CRASHED` 的后缀躺在证据库里。
